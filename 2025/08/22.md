PostgreSQL's `ltree` extension stores hierarchical paths as dot-separated labels: `europe.germany.munich`. You can query ancestors, descendants and subtrees with operators like `@>` and `<@`. What it does not give you out of the box is a way to export a subtree as nested XML — which is what you need when a legacy consumer expects a document structure rather than flat rows.

This PoC was built with AI Studio assistance. The core is a single plpgsql function, `generate_xml_from_tree`, that walks any subtree from a given node to a given depth and returns nested XML.

## Schema and data

The table design stores every node in a single relation. The `path` column is `ltree`; the rest is metadata.

The function in `01_function.sql` uses a recursive CTE to collect the subtree, then builds nested XML by walking depth levels from the root down. It is parameterised: pass a starting node ID and a maximum depth, and it returns only the relevant portion of the tree.

## Running it

Everything is containerised. The Dockerfile extends the official PostgreSQL image and installs the `ltree` extension. `make build` builds the image, `make start` brings up the container, `make test` runs the validation queries.

<div class="snippet-tabs"
     data-tabs="Dockerfile|dockerfile|Dockerfile,Makefile|makefile|Makefile,Tests|sql|test.sql"

`make test` calls `test.sql`, which exports several subtrees at different depths and prints the XML. A passing run looks like this:

```bash
$ make test
...
<node id="1" label="root">
  <node id="2" label="europe">
    <node id="5" label="germany">
      ...
    </node>
  </node>
</node>
```

## Notes on AI Studio

This example was written with [AI Studio](https://aistudio.google.com/). At the time of writing, AI Studio cannot execute code, so the human-in-the-loop is still required to catch subtle mistakes that would surface at runtime. Asking it to generate tests alongside the implementation is a useful forcing function — even in those tests you will find edge cases it missed. After a few iterations the result works cleanly.

The Python helper (`app.py`) connects to the container and can be used to call the function programmatically rather than through `psql`.
