The prompt was direct: build a rebar3 Erlang todo list application with SQLite storage, an HTTP API, and a small HTML UI. Target platform Ubuntu, Erlang installed, use only what ships with OTP. GPT-5 produced a complete, working OTP application in a single response.

What follows is a walkthrough of the structure — where the pieces fit, what non-obvious choices were made, and what you would change for production use.

## The supervision tree and application module

<div class="snippet-tabs"
     data-tabs="todo.erl|erlang|todo.erl,todo_app.erl|erlang|todo_app.erl,todo_sup.erl|erlang|todo_sup.erl"
     data-github="2025/08/28"></div>

`todo.erl` is the public API module — `add/1`, `list/0`, `del/1`. These are the functions you call from `curl` via the HTTP handlers, or directly from an Erlang shell. Keeping them as ordinary functions makes them testable without involving the HTTP layer at all.

`todo_app.erl` starts two things: the database connection and the HTTP server. The supervisor uses `one_for_all` because if either child fails, the other is in an undefined state — the HTTP server cannot serve requests without a database.

## Storage and HTTP

<div class="snippet-tabs"
     data-tabs="todo_db.erl|erlang|todo_db.erl,todo_http.erl|erlang|todo_http.erl,rebar.config|erlang|rebar.config"
     data-github="2025/08/28"></div>

`todo_db.erl` wraps the `esqlite` NIF. The database file is created under `priv/todo.db`; the directory is ensured at startup. The JSON encoding uses the built-in `json` module from OTP 27+ — no external dependency.

The HTTP layer uses `inets` httpd with `mod_esi`. The prefix `/todo` maps to the `todo_http` module, so `GET /todo/add` calls `todo_http:add/2`. It is minimal but sufficient for a demo: all responses return 200 with a JSON body indicating success or failure.

`rebar.config` includes a `shell` config that auto-starts the `todo` application when you run `rebar3 shell`. That means `rebar3 shell` and you are immediately ready to test.

## HTML UI

<div class="snippet-tabs"
     data-tabs="index.html|html|index.html"

The UI lives in `priv/index.html` and is served statically. It calls the same JSON endpoints as `curl`. Nothing surprising here — the main value is that it demonstrates the endpoint contract through a browser without needing a separate client.

## Building and running

```bash
sudo apt-get install -y erlang-base erlang-dev build-essential libsqlite3-dev
rebar3 shell
```

Test from a second terminal:

```bash
curl "http://127.0.0.1:8080/todo/add?text=Read%20Erlang%20docs"
curl "http://127.0.0.1:8080/todo/list"
curl "http://127.0.0.1:8080/todo/del?id=1"
```

## What GPT-5 got right and what it did not

**Right:** The OTP application structure, the `mod_esi` routing pattern, the `esqlite` dependency declaration, the `one_for_all` supervisor choice. These are not obvious to someone learning Erlang — they require understanding OTP conventions.

**Needs attention for production:**
- No concurrent access control on the SQLite handle — fine for a demo, a problem under load.
- `mod_esi` uses URL parameters for mutation (`GET /todo/add`) rather than `POST`. Acceptable for a demo; not RESTful.
- The `priv/todo.db` path is absolute to the release — add `RELEASES` handling if you intend to deploy with `rebar3 release`.
