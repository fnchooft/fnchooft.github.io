Connection failures in a distributed system can be intermittent, direction-specific, and percentage-based rather than binary. A client that loses 20% of packets to a primary database will see elevated latency and occasional timeouts, not a clean failure. That is exactly the class of failure that is hardest to reproduce in a development environment.

This setup uses Docker Compose with Linux traffic control (`tc`) to inject packet loss between specific containers. The topology: a Postgres primary, a Postgres secondary with streaming replication, an HAProxy load balancer, and three clients. Any pair of nodes can have loss introduced and removed independently with a shell script.

The custom Postgres image adds `iproute2` on top of the official image. Without it, `tc` is not available inside the container and you cannot manipulate the network interface. The `NET_ADMIN` capability in the compose file is also required — `tc` needs it to modify qdiscs.

HAProxy is configured in active/backup mode: it routes to the primary and falls back to the secondary if the primary becomes unreachable.

## Injecting packet loss

Each scenario targets a different link. Scenario 1 adds 20% loss from the primary database toward the proxy. Scenario 2 targets the secondary. Scenario 3 targets a specific client. Loss is unidirectional — the return path is unaffected, which models real asymmetric degradation.

`tc` uses an HTB qdisc with a `netem` child to apply the loss. The scripts find the container's `eth0` interface, identify the IP of the proxy, and create a filter that matches traffic destined for that IP.

## Verifying replication

Start the stack with `make all`. Wait about two minutes for the secondary to complete its initial sync — you can watch progress with `docker logs db-secondary` and wait for the `streaming WAL` message.

```bash
# Check replication is active on the primary
docker exec db-primary psql -U user -d postgres -p 5433 \
  -c "SELECT * FROM pg_stat_replication;"

# Write on the primary
docker exec db-primary psql -U user -d postgres -p 5433 \
  -c "INSERT INTO users(name,email) VALUES ('Anton','anton.aus@tirol.de');"

# Read back on the secondary
docker exec db-secondary psql -U user -d postgres -p 5433 \
  -c "SELECT * FROM users;"
```

Then inject loss and repeat the read from a client through the proxy. You will see intermittent delays and occasional retries that your application layer needs to handle gracefully.
