A release portal is a common internal tool: engineers log in, see which software releases they are authorised to download, and fetch the artefact files. The access rules are per-user per-release, with separate rights for different artefact types (source tarballs, binary packages, documentation).

This OTP application implements that pattern using `inets` httpd as the HTTP server, `mod_esi` for dynamic routing, `mod_auth` for basic authentication, and a small XML catalogue format for release metadata. No external dependencies.

## Application and supervision structure

`release_portal_app.erl` starts the inets httpd server before calling the supervisor. The HTTPD configuration routes all traffic under `/download` through `mod_esi` to the `release_portal_service` module. `mod_auth` secures the download directory with a plain-text password file.

The supervisor uses `one_for_all` with intensity 0, period 1 — any child failure brings down the whole application immediately. For a portal that serves files from disk this is intentional: a crashed service module should not leave the HTTP server accepting connections it cannot route correctly.

## Service, parser, and view

<div class="snippet-tabs"
     data-tabs="release_portal_service.erl|erlang|release_portal_service.erl,release_portal_parser.erl|erlang|release_portal_parser.erl,release_portal_view.erl|erlang|release_portal_view.erl"
     data-github="2025/11/03"></div>

`release_portal_service.erl` handles two routes. `GET` renders the download page for the authenticated user — it calls into `release_portal_logic` to get the filtered release list and `release_portal_view` to render HTML. `GET /download/:RELEASE/:VERSION/:FILE` performs the access check and then calls `mod_esi:deliver_file/2`.

The access check in `can_user_download/4` is worth examining: it first checks whether the user has rights to the release name, then parses the XML catalogue for that release/version, finds the specific file's artefact type, and checks whether the user's rights include that type. Two layers of authorisation: release-level and artefact-type-level.

`release_portal_parser.erl` uses `xmerl` to parse the catalogue XML. The parser produces `#release{}` records with `#artifact{}` children using the record definitions from `release_portal.hrl`.

## Building and running

```bash
rebar3 compile
rebar3 shell
```

The `priv/` directory needs to be populated with:
- `htdocs/` — static files including `index.html`
- `htdocs/download/` — the directory protected by `mod_auth`
- `auth/passwd` and `auth/group` — plain-text credential files in Apache format
- `releases/:name/:version/:file` — the actual release artefacts
- `catalog/:name-:version.xml` — XML metadata files describing each release
