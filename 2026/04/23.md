GitBook's asset inclusion syntax — `{% include %}` and similar directives — does not survive outside the GitBook pipeline. If you want to publish the same markdown on GitHub Pages or any other static site, the includes need to be resolved before the files leave the repository. This workflow does that as a CI step.

The approach: a Python script scans all markdown files for `<!-- include: path -->` comments, reads the referenced files, and injects their content inline. A GitHub Actions workflow runs this script on every push to `main`, commits the resolved output to a separate `gitbook` branch, and pushes it.

`inject_snippets.py` walks the repository, finds every markdown file, and looks for comment pairs:

```markdown
<!-- include: path/to/file.c lang=c -->
<!-- /include -->
```

On the first run the content between the tags is empty. On subsequent runs the existing content is replaced. The script is idempotent: running it twice on the same file produces the same output.

The workflow runs on `push` to `main`. It checks out the repo, runs the script, and if any files changed it commits and pushes the result to the `gitbook` branch. GitBook is configured to publish from that branch, so it always sees resolved content.

## Why this matters

Without the injection step, code snippets in the GitBook source are references (`<!-- include: ... -->`). If a referenced file changes and the include is not re-resolved, the published documentation goes stale silently. The CI step makes the reference a compile-time dependency: the docs branch only updates when the script runs successfully.

The limitation is that the `gitbook` branch diverges from `main` in history. Reviewers need to remember that `main` is the source of truth and `gitbook` is the derived output — reviewing the `gitbook` branch directly is misleading.
